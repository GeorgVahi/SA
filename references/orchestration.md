# Чистые роли, владение и продолжение

## Роли и dispatch

Один координатор владеет Endpoints после inventory-фазы, State, сводками, каноническими статусами Tasks в remediation, расписаниями и мутирующим Git. Роли владеют только назначенными артефактами/исходниками. Общий формат — [artifacts.md](artifacts.md).

Для каждой новой роли используй `fork_turns="none"`, уникальное имя с run/work/phase/round и отдельный agent ID. Не назначай модель/effort, не передавай историю чата, желаемую оценку, предполагаемый ответ или пересказ доказательств как факт. Передавай пути к первичным документам и текущему коду. Общий диск не означает общий контекст. При отсутствии механизма чистых ролей оставь частичный результат; собственной проверкой независимость не заменять.

В каждом задании явно укажи: корень проекта и скилла; выбранный режим и одну роль; endpoint/work/issue ID и раунд/попытку; обязательные reference-файлы; исходный документ и входные версии; разрешённые файлы; уже выданные полномочия и исключения; требуемый вердикт/артефакт. Агент читает AGENTS сам. Он не один в проекте, сохраняет чужие изменения, не запускает дополнительных агентов, не управляет goal/State/расписаниями/установкой/Git и не выходит за разрешённую область. Все роли наследуют границы безопасности SKILL через явное задание, а не недоступную историю.

Аудиторские задания:

- Inventory: самостоятельно сверить Endpoints с регистрацией; владение только Endpoints и Inventory Review; приложение не менять.
- Audit одного endpoint: профиль, fingerprint и отдельные доказанные Tasks; читать artifacts/checks; общие файлы и приложение не менять; вернуть ready_for_review и версии.
- Review одного endpoint: код, профиль, все Tasks и основание reuse/отсутствия находок; владение только своим Reviews; вернуть accepted/changes_requested/blocked и точную версию. Приложение и чужие артефакты не менять.

Задания четырёх remediation-ролей — [remediation.md](remediation.md). Не включай их в аудиторскую линию и не выдавай audit-review за code-review фикса.

## Слоты и блокировки

Определи фактически свободные активные слоты, учитывая координатора, родителей и вложенных агентов. Не фиксируй число 4/8 в скилле. Одна линия имеет только одну активную фазу. Разные линии параллельны по доступности; неизвестный лимит означает одну линию. Capacity error — дождаться освобождения, а не повторять spawn в цикле или подменять внутренние роли отдельными пользовательскими чатами.

Храни владение артефактами и источниками в State. Запись одной линии не должна пересекаться с записью или влияющим чтением другой. Read/read на общей зависимости допускается при согласованной версии. С момента внедрения до принятия code-review удерживай write-блокировки изменяемых файлов и read-блокировки влияющих зависимостей. Общий изменяемый service/middleware/schema/lockfile сериализует линии. При неизвестной closure сериализуй внедрения. Расширение набора записи требует нового принятого плана до изменения нового файла.

Канонический общий дефект исправляет один владелец. Остальные исходные файлы ждут общего результата, затем проходят собственные четыре свежие роли применимости; третий агент может доказанно использовать уже внедрённый код без второго патча. Канонический resolved принимается только для всех затронутых endpoint-контекстов. Не копируй вывод первого ревьюера как независимое подтверждение остальных.

## Checkpoint и остановленные роли

Используй schema 2 из artifacts, поддерживая прежние данные. Сохраняй checkpoint при каждой смене фазы, вердикте и перед финалом; запись должна оставлять последний корректный документ при I/O-сбое (временный файл и безопасная замена в той же папке). Unknown incompatible schema не обнулять.

После компакции/рестарта восстанови mode/scope, версии входных документов и кода, no-progress счётчики и active time. Проверь реально работающие роли. Timeout/исчезновение из списка не доказывает освобождение файлов: до повторной записи подтвердить завершение или остановку прежнего владельца. При неизвестном состоянии не запускай второго писателя. Запоздалый вердикт другой attempt ID отвергай. Сохраняй историю; не стирай последствия его фактической записи без проверки.

После прерванного внедрения прочитай фактический baseline/diff и завершённость проверок, затем выбери продолжение, новое ревью или перепланирование; патч повторно вслепую не применять. После частичной записи Code Reviews/source/Tasks/State сверить принятую версию с текущим кодом и идемпотентно завершить синхронизацию. Неполная связка или противоречивые актуальные решения — blocker до нового независимого решения.

## Раунды без продвижения

Общего потолка числа попыток/волн нет. Для планирования, внедрения каждой линии и full-волн раздельно сохраняй consecutive_no_progress, причину и доказательства сброса. Пауза, ожидание слота и рестарт не являются завершённым раундом; новый agent/run ID не обнуляет счётчик неизменной проблемы.

Продвижение — доказанно закрытый невыполненный критерий, новый принятый результат фазы, устранённый путь нарушения или снятая обязательная проверочная блокировка. Пересмотренный план требует новой подтверждённой причины, существенно другого способа и принятого независимого решения с проверяемым сигналом. Косметический diff, переименование и обещание успеха не являются прогрессом; повторное закрытие вновь внесённого самим процессом дефекта не даёт нового прогресса.

После трёх последовательных завершённых раундов/волн без продвижения — одна целевая переоценка новым планировщиком и новым независимым ревьюером. Если другой путь доказан и принят, продолжить на новой базе со сбросом счётчика и историей. Если нет — сохранить конкретный blocker, checkpoint и продолжить независимые задачи. Без новых данных переоценку не повторять. Эти workflow-условия не заменяют точные правила goal blocked/paused/complete.

## Время, прогресс и ETA

Во всех режимах подробная сводка раз в **3600 секунд активной работы**. Active включает ожидание работающих ролей и исключает пользовательскую паузу/неработающий сеанс. Накопление и last_report_active_seconds сохраняются; после компакции отсчёт не начинается заново. Во время active-ожиданий координатор регулярно просыпается для проверки завершённых ролей и времени; один блокирующий wait не должен задерживать отчёт. Обычные короткие updates по правилам среды сохраняются.

Сводка: режим/фаза; обработанные исходные файлы X/N и оставшиеся; accepted/reused audit endpoints при применимости; уникальные issues resolved/already_resolved/rejected/active/blocked; текущие фазы, последние значимые результаты; ETA диапазон и его основание. Дубликаты считать по canonical ID; блокировки показывать отдельно от числа работающих задач.

ETA выводить после минимум трёх сопоставимых завершённых линий либо достаточных измерений отдельных фаз. Учитывай оставшиеся фазы, эффективные слоты и последовательный критический путь/блокировки общих файлов; не дели всё время на номинальную capacity. Без базы — «данных для надёжной оценки пока недостаточно». Снятие внешнего blocker имеет неизвестное время и не скрывается внутри уверенного диапазона.

Для отдельно запрошенной доставки при неактивном чате найди/создай доступный heartbeat того же чата через automation_update; не создавай дубликат, cron или новый чат. Prompt читает checkpoint и даёт запрошенную часовую сводку без запуска конкурирующего процесса и записи артефактов. Сохрани ID, останови на финале. Без планировщика доставка только во время активного запуска; один файл скилла не обеспечивает фоновое исполнение при закрытом приложении.
