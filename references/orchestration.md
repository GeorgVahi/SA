# Оркестрация и чистые контексты

## Обязательные роли

Координатор читает текущие артефакты, управляет очередью, goal, временем и доступными слотами. Он не выдает собственное заключение за независимое ревью. Проверка инвентаря предшествует всем endpoint-линиям; только ее агент может редактировать общий список на этой фазе. После нее общий `Endpoints.md`, `State.json`, `Summary.md` принадлежат координатору.

Не передавай историю чата, вывод другого агента в тексте задания, предполагаемый ответ или собственные подозрения. Передавай пути к сырым артефактам; ревьюер неизбежно читает отчет аудита как предмет ревью, но сам проверяет его по коду. Доступ к общему диску не означает общий контекст. Каждый агент читает применимые `AGENTS.md` и указанные reference-файлы сам.

Для каждого нового агента: `fork_turns="none"`, уникальное имя с фазой и ID, модель/effort по настройкам среды. В другой среде используй эквивалент создания нового агента **без наследования истории**. Отсутствует такой механизм — зафиксируй ограничение, не выдавай аудит одного агента за две независимые фазы.

## Пример задания проверки инвентаря

> Проверь инвентарь эндпоинтов проекта `<root>` для скилла SA `<skill>/SKILL.md`. Прочитай применимые AGENTS.md и `<skill>/references/artifacts.md`. Самостоятельно сопоставь `Security Audit/Endpoints.md` с кодом регистрации, префиксами и вызываемыми извне операциями. Добавь недостающие эндпоинты, исправь неверные сведения, сохрани доказательство охвата в `Security Audit/Inventory Review.md`. Ты владеешь только этими двумя файлами. Ты не один в проекте; сохраняй чужие изменения. Код приложения не меняй. Не управляй goal, git или расписаниями. Если полноту подтвердить нельзя, укажи конкретную область и причину.

## Пример задания аудитора (один endpoint)

> Проведи фазу аудита только эндпоинта `<id>` в проекте `<root>` по скиллу `<skill>/SKILL.md`. Прочитай применимые AGENTS.md, references/artifacts.md и references/checks.md. Исходная запись — `Security Audit/Endpoints.md`. Проверь предыдущий профиль и всю влияющую dependency closure по текущему диску; при достаточном доказательстве неизменности предложи переиспользование, иначе выполни аудит всех категорий. Запиши профиль и отдельные подтвержденные задачи. Ты владеешь только `Profiles/<id>.md`, `Fingerprints/<id>.json` и `Tasks/<id>-*.md` внутри Security Audit. Общие файлы и приложение не меняй. Ты не один в проекте; сохраняй чужие изменения. Не управляй goal, git и расписаниями. Верни список артефактов, fingerprint, ограничения и статус ready_for_review. Внешние запросы и реальные данные не разрешены.

## Пример задания ревьюера (один endpoint)

> Независимо проверь только эндпоинт `<id>` проекта `<root>` по скиллу `<skill>/SKILL.md`. Прочитай применимые AGENTS.md, references/artifacts.md, references/checks.md и сырой текущий код. Предмет ревью: запись Endpoints.md, Profiles/<id>.md, Fingerprints/<id>.json и все Tasks/<id>-*.md внутри Security Audit. Проверь каждую находку, полноту категорий, отсутствие пропусков и основание переиспользования, если оно заявлено. Не считай вывод аудитора доказательством. Ты владеешь только `Reviews/<id>-<round>.md`; другие артефакты и приложение не меняй. Ты не один в проекте; сохраняй чужие изменения. Не управляй goal, git и расписаниями. Верни accepted либо changes_requested с конкретными основаниями и проверенным fingerprint. Внешние запросы и реальные данные не разрешены.

Если ревью возвращает замечания, действующий аудитор этой же линии или новый редактор получает только перечень требуемых правок и правит свои артефакты. Следующее ревью выполняет новый чистый агент. Не сохраняй отклоненную гипотезу как открытую уязвимость: убери ее из списка подтвержденных, а причину отклонения оставь в ревью. Невыполнимую проверку оставь ограничением, не переименовывай в accepted.

## Слоты и параллелизм

Перед dispatch определи доступное число **активных** слотов из инструментов/текущих агентов. В лимит входят координатор, вложенные агенты и остальные активные задачи. Не фиксируй число вроде 4/8 в скилле. При свободных слотах запускай столько разных endpoint-линий, сколько помещается; в одной линии одновременно активна только одна фаза. После завершения аудитора дождись освобождения слота и запускай нового ревьюера. Не держи завершенную фазу активной ради повторного использования.

Не допускай конкурентных писателей одних файлов. Задачи одного общего дефекта привяжи к одному каноническому issue и перечисли затронутые endpoint ID; координатор объединяет дубликаты после завершения владеющих линий и до финальной приемки. Затронутые профили должны ссылаться на каноническую задачу и принятое ревью этой связи.

Если лимит неизвестен, запускай одну линию, учитывая координатора. Ошибка capacity — не причина многократно повторять spawn: дождись завершения активной задачи, затем попробуй заново. Не переключайся на отдельные пользовательские чаты через create_thread вместо внутренних сабагентов.

## Checkpoint, goal и отчеты

В `State.json` сохраняй ID запуска, время начала, накопленное активное время, время последнего двухчасового отчета, ID goal/heartbeat (если применимы), состояния endpoint-линий, пути артефактов и причины блокировок. При возобновлении не доверяй статусу running: проверь реальные агенты; при исчезнувшем агенте верни линию в очередь. Перепроверь инвентарь и версии после изменений кода.

Два часа считаются по реальному времени активного аудита, включая ожидание работающих сабагентов, но исключая пользовательскую паузу/закрытый сеанс. После компакции восстанови время из checkpoint, не начинай отсчет заново. Пиши обычные короткие progress updates по правилам среды; подробный отчет раз в два часа их не заменяет.

Формат отчета: `Принято X/N (из них K переиспользовано); подтверждено F уникальных проблем, критических C; осталось R, блокировано B; ориентировочно T по среднему времени M завершенных линий.` Если данных мало, скажи, что надежной оценки пока нет. Считай только принятые ревью задачи; pending находки показывай отдельно. Проверенный endpoint с уязвимостью может быть завершен: исправление приложения не входит в SA.

Для отдельно запрошенной фоновой доставки используй доступный thread-heartbeat через automation_update. Найди существующий SA heartbeat этого запуска, не создавай дубликат. Промпт: читать актуальный checkpoint, сообщать двухчасовую сводку по этому аудиту, не запускать конкурирующих аудиторов и не менять артефакты; при финале остановить heartbeat. Сохрани ID. Без планировщика честно обозначь доставку только во время активной сессии. Не обещай, что один SKILL.md обеспечивает автономный процесс при закрытом приложении.

Финал: снова сопоставь маршруты с инвентарем и проверь отсутствие добавленных/удаленных endpoint-ов. Для каждого есть актуальный fingerprint, полный профиль и принятое независимое ревью (включая reused). Нет running/pending/stale/blocked и материально непроверенных категорий. Тогда сформируй Summary.md и закрой только принадлежащий SA goal; иначе сохраняй checkpoint, продолжай доступную работу и соблюдай точные условия blocked/paused инструмента.
