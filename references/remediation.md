# Исправление замечаний: fix и full

Исправляй только актуальные подтверждённые замечания выбранной области. Четыре последовательные свежие роли на исходный файл: план → ревью плана → внедрение → ревью кода. Используй [контракты](artifacts.md), [владение и продолжение](orchestration.md), [доказательства](checks.md) и [форматы источников](artifact-formats.md).

## Подготовка координатором

1. Прочитай AGENTS/README/owner-документы и State. Зафиксируй mode/scope/run, реальные dirty/untracked изменения и исходный реестр всех файлов в Endpoint Reviews рекурсивно, включая фактический формат/кодировку. Используй соответствующий обработчик; неизвестное расширение не исключает файл.
2. Если прежний SA имеет только Profiles/Tasks/Reviews, подготовь Endpoint Reviews со ссылками без удаления/переноса истории. Существующие исходные документы не перезаписывать шаблоном. Для каждого файла назначь work ID, для уникального дефекта — canonical issue ID, сохрани все endpoint/source связи. При недоказанном mapping укажи конкретное ограничение, а не придуманный маршрут.
3. Проверь актуальную регистрацию затронутых endpoint и access contract. В `fix` автоматически полный аудит остальных маршрутов не запускается. Непринятые старые гипотезы не дают права исправить приложение: планировщик и ревьюер сначала доказывают их актуальность. Файлу без записанных замечаний присвой no_recorded_findings и оценку —; это не новый аудит отсутствия уязвимостей.
4. Приоритет critical → high → medium → low, затем стабильный порядок путей. Учти общий дефект и блокировки before dispatch. Исходные input-версии и исходно актуальные findings сохранить, чтобы общий фикс этого запуска не превратился в фиктивное already_resolved.
5. В `full` сначала зафиксируй принятые доступные результаты аудита без конкурирующих аудиторов, затем эту очередь. Непроверенные области остаются blocker всего full. Не меняй синтетическую/ручную запись на confirmed без новой доказательной проверки.

## 1. Новый планировщик

Минимальное задание: «Режим <fix/full>, только planning work <id>, source <path>, issue IDs <ids>, проект <root>, скилл <skill>. Прочитай SKILL, artifacts/checks/remediation/artifact-formats и AGENTS. Перепроверь текущие находки по кодовой цепочке и контракту. Владеешь только Plans/<work>-<round>-<version> и снимками этой фазы/попытки. Приложение не менять. Верни план, версии, первичный сигнал и ограничения». Добавь общие запреты и конкретные полномочия из orchestration.

План содержит для каждого замечания:

- source/endpoint/issue ID, исходные ссылки/локаторы, нарушенный контракт, вход и реальный эффект;
- актуальные code/input manifests, полную dependency closure и основания её полноты, внешние влияющие условия;
- текущий статус подтверждения и узкий первичный сигнал;
- корневой ответственный слой и минимальное связное изменение, разрешённые исходники/тесты, влияние на другие endpoints и зависимости от общих фиксов;
- последовательность, объективные критерии устранения, обязательные positive/negative regression checks и ожидаемые результаты;
- необходимые совместимость/миграция/rollout и условия проверки; отдельно ограничения;
- способ записи итогового вердикта в исходный формат без потери ручных данных.

Для поведения нужен практический падающий сигнал до изменения: локальный regression test/воспроизведение с синтетическими данными. Если выполнить его невозможно, допустима полная проверяемая цепочка с явным ограничением; приёмка всё равно требует выполнимых необходимых проверок. Не выдавай отсутствующий runtime или ошибки инструментов за passed. Не создавай тест, повторяющий строки реализации.

Если замечание устранено до этого запуска или ошибочно, запиши доказательство и предложи already_resolved/rejected, не фиктивный патч. Если устранено общей линией текущего запуска, предложи проверку применимости этого фикса и необходимые отдельные изменения; четыре роли сохраняются.

## 2. Новый ревьюер плана

Минимальное задание: «Только plan_review work <id>, source <path>, plan <version/path/digest>. Самостоятельно прочитай текущий код/контракт, входные документы и сигналы; проверь каждое замечание, выбранный слой, closure/ownership, применимость общего фикса и критерии. Владеешь своим Plan Reviews и новой версией плана/снимками этой попытки, не приложением. Верни accepted/changes_requested/blocked и точные принятые версии». Не передавай желаемый ответ или историю автора.

Ревьюер может дополнить план, создав новую immutable редакцию с новым номером/digest, описанием дополнений и собственной проверкой конечного содержания. Предыдущую редакцию/решение сохранить. Любая последующая содержательная правка требует ещё одной версии и нового независимого ревью. Accepted означает проверенный конечный план, baseline и входные finding-контракты, не просто одобрение идеи.

Если все записи независимо доказаны already_resolved до начала запуска либо rejected, завершить линию без фиктивного внедрения/числовой оценки. Координатор получает ownership исходника после завершения роли, записывает эти статусы, историю, оценку — и ссылку на принятое Plan Reviews в исходный формат и проверяет сохранность/повторное чтение; отдельная роль внедрения или code review для отсутствующего патча не выдумывается. При неудавшейся записи линия остаётся незавершённой. Для полностью прочитанного файла без записанных замечаний достаточно реестра и таблицы: запись в исходник `not_required` с основанием. При blocker сохранить причину. Для общего фикса этого запуска не подменять собственные четыре роли ссылкой на первого ревьюера.

## 3. Новый исполнитель

Минимальное задание: «Только implementing work <id>, accepted plan <path/version/digest>, разрешённая запись <files>, полномочия <exact>. Перед записью сверить baseline/input/plan и получить ownership координатора. Реализовать план и необходимые regression checks, сохранить Implementations и свои before/after snapshots. Не выставлять окончательный resolved, не писать чужие источники/State/Tasks и не выполнять Git-мутации».

До изменения отличить чужие dirty/untracked bytes от будущего task-owned diff. Сравнение только с HEAD не устанавливает авторство. При неотделимом конфликте — blocker, без stash/reset/отката. Не применять stale план; источник изменения сначала выяснить, согласованный patch другой prerequisite-линии проверить по новой принятой применимости.

Исправляй слой причины без дублированных fallback/защитного состояния ребёнка и форматного churn. Новая область записи/способ/критерий требует перепланирования и нового ревью до расширения патча. Generated-файлы обновлять штатным генератором по правилам проекта; вручную — только по явному правилу и принятому плану. Не устанавливать новые production-зависимости или инфраструктуру без полномочий.

Запускать узкие необходимые проверки, затем расширять по конкретному риску. Сохранять actual команды, exit codes, primary red/green, changed files, task-owned diff и ограничения. Показать, что тест выявлял нарушение исходной версии, а после патча допускает правильное поведение. Не повторять одинаковые успешные проверки ради количества. Общий уже внедрённый код проверять для своего endpoint; отсутствие повторного патча явно записать.

## 4. Новый ревьюер кода

Минимальное задание: «Только code_review work <id>, source <original path>, accepted plan/implementation <paths>, текущий код и task-owned diff. Независимо проверить исходный сценарий, существенные обходы, допустимое поведение, выполненные/обязательные проверки и точную closure. Код приложения и тесты не менять. Владеешь только своим Code Reviews, исходным документом этого work и снимками попытки. Запиши отдельные status/verdict/score/rationale/evidence/version по каждому issue и верни их координатору».

Ревьюер сам выполняет безопасный необходимый сигнал; отчёт исполнителя не заменяет независимость. Доказанные новые дефекты патча блокируют приёмку. Старую стороннюю проблему вне scope можно доказательно записать отдельно, но нельзя молча расширить fix до полного аудита/нового патча.

Приёмка каждого issue — актуальное accepted review, прекращение достижимости исходного нарушения и существенных обходов при сохранении допустимых действий, успешные обязательные проверки. Оценка 1–10 описывает качество, числового порога нет. Несогласованность числа/вердикта требует объяснить доказательства, а не автоматически закрыть issue по баллу. Failed/timeout/обязательная непроверенная область не превращаются в resolved. Шкала, все статусы и локальная область приёмки — artifacts.

Записать verdict, статус, score (или — без нового фикса), объяснение, проверенную версию и ссылки в тот же исходный файл его обработчиком. Сохранить ручные данные и историю, проверить повторное чтение/структуру/визуальную сохранность по формату. Запись result-полей своей фазы — ожидаемый diff, а изменение смысла finding-контракта требует актуализации. Отдельный report не заменяет неудавшуюся запись в источник.

## Возвраты, синхронизация и финал

Координатор сверяет полную связку: принятое план/code решение, implementation, source history, task, версии и State. Канонические Tasks обновляет по вердикту, не собственному заключению. Для общего issue все endpoint-контексты должны иметь accepted применимость на актуальной версии. После сбоя завершить синхронизацию идемпотентно, не объявлять частично записанную связку завершённой.

После changes_requested — новый исполнитель и новый ревьюер; при изменении способа/файлов/критериев — сначала новый план и plan-review. Используй счётчики трёх последовательных раундов без продвижения из orchestration; продуктивная работа не ограничена числом попыток. После целевой переоценки без другого обоснованного пути сохранить blocked и продолжить остальные линии.

В `fix` изменившиеся исторические Profiles пометить stale: приёмка исправления не является полным переаудитом. В `full` после согласованного пакета исправлений выполнить завершающий audit затронутых endpoints двумя новыми ролями на каждый; неизвестная область влияния расширяет проверку до всего инвентаря. Новые independently confirmed findings возвращать в очередь. Отслеживать full-волны без продвижения, не повторять полный аудит после каждого одиночного патча.

Перед итогом заново перечислить источники, сопоставить semantic input-версии, code closure и актуальные вердикты. Новые/изменённые замечания вернуть в подготовку; удалённые документы/endpoint не терять из истории. Сформировать Remediation Summary и сообщение с таблицей **Файл | Эндпоинт | Замечание | Оценка**, одна строка на finding и отдельная строка для источника без findings/с препятствием. Дубликаты отражены во всех источниках, но уникальный счётчик по canonical issue.

Полный успех требует каждого учтённого источника, доказанного resolved/already_resolved/rejected каждого canonical issue, согласованных актуальных версий и отсутствия pending/partial/blocked/stale/ожидающего ревью. Full дополнительно требует полного принятого актуального аудита. Иначе checkpoint и честный частичный итог с остатком, фактическими первичными/независимыми проверками, состоянием rollout и commit/push. Публикация security-отчётов требует отдельной авторизации.
