# Аудит эндпоинтов

Этот процесс действует для `audit` и аудиторских фаз `full`. Код приложения не менять. Используй общие [роли и checkpoint](orchestration.md), [контракты](artifacts.md) и [доказательства](checks.md).

## Координатор

1. Прочитай применимые AGENTS, README и документацию маршрутов. Найди существующий список и `Security Audit/`. Наличие папки не доказывает полноту. Если Endpoints отсутствует, составь его по фактической регистрации и документации; если есть — сверяй заново.
2. Учитывай методы, префиксы, версии, вложенные роутеры, вебхуки, загрузки, framework-generated маршруты и вызываемые извне RPC/GraphQL-операции. Назначь стабильные endpoint ID, укажи регистрацию, обработчик и доступ. При нулевом инвентаре тоже сохраняй доказательство поиска.
3. Новый чистый inventory-agent самостоятельно сопоставляет Endpoints с кодом, исправляет пропуски и сохраняет Inventory Review. До принятой полноты endpoint-аудит не начинается. Неизвестные области остаются blocker.
4. Для каждого эндпоинта выполняй два последовательных новых чистых агента: аудитор → независимый ревьюер. Разные endpoint-линии можно вести параллельно в свободных слотах. Не переиспользуй роли или историю.
5. Аудитор читает текущий код и прежний профиль. Reuse допустим только по доказанному совпадению актуальной полной dependency closure, bytes, access contract, релевантных внешних условий, категорий и принятого прошлого ревью. Неизменный handler или commit SHA недостаточны. Без надёжной базы выполнить аудит заново.
6. Для всех 12 категорий из checks сохранить checked/not_applicable/blocked и доказательство/основание. Только подтверждённые дефекты записывать отдельными задачами. Не подтверждённые идеи и недоступные проверки остаются ограничениями, а не задачами с выдуманным эффектом.
7. Новый ревьюер сам читает текущий код, профиль и каждую задачу, проверяет access contract, достижимость, severity, ссылки, предлагаемое исправление, полноту категорий и вывод «нет находок». Reuse тоже требует нового решения. Вердикт accepted привязать к точному fingerprint и содержанию документов.
8. После changes_requested исправить только артефакты этой линии и назначить очередного нового ревьюера. Невыполнимую проверку не переименовывать в accepted. Изменение влияющей версии во время аудита делает результат stale и требует повторить обе фазы.
9. После принятия координатор создаёт/согласует Endpoint Reviews со ссылками на профиль, ревью и канонические задачи. Не перезаписывать прежний ручной документ шаблоном; сохранять историю. Файл без находок явно содержит 0 записанных подтверждённых проблем. Это подготовка артефактов, а не дополнительное независимое заключение.
10. Перед итогом снова сверить текущие маршруты, версии, полный профиль и принятые решения. Добавленные маршруты включить в очередь; удалённые сохранять исторически с removed. Не объявлять полное покрытие при blockers/stale/pending или неподтверждённом пропуске.

## Передача в исправления

В `audit` после Summary остановись: найденные проблемы ещё не исправлены. В `full` дождись завершения всех доступных аудиторских линий без конкурирующих писателей, зафиксируй аудит и переходи к remediation только по независимо принятым находкам. Blocked области не запрещают независимые исправления, но весь `full` остаётся частичным.

После исправлений `full` определяет множество затронутых эндпоинтов по актуальному графу зависимостей. Для них снова выполнить обе свежие аудиторские фазы и все категории. Неизменные результаты переиспользовать лишь по прежним строгим правилам; при недоказанной полноте области влияния проверить весь инвентарь. Новые принятые находки возвращаются в remediation. Ожидаемые изменения самого фикса не считать внешним конфликтом; прежний аудит изменившегося кода не выдавать за текущий.
