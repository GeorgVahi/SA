# Инвентарь, версии и артефакты

## Структура внутри проверяемого проекта

```text
Security Audit/
  Endpoints.md
  Inventory Review.md
  State.json
  Summary.md
  Profiles/<endpoint-id>.md
  Fingerprints/<endpoint-id>.json
  Tasks/<endpoint-id>-<issue-id>.md
  Reviews/<endpoint-id>-<round>.md
```

Сохраняй существующие результаты и ручные изменения. Если старый формат не содержит нужных доказательств, дополни его или переаудируй; не удаляй всю папку. Историю значимых ревью/переаудита сохраняй отдельным раундом/запуском. Старые задачи не являются доказательством, что проблема осталась или исправлена: перепроверь и зафиксируй их актуальный статус. Не удаляй вручную написанные задачи молча.

## Endpoints.md

Метод + нормализованный зарегистрированный путь + сервис/версия определяют endpoint. Разные методы — разные записи. Для RPC/GraphQL одна транспортная запись с отдельными дочерними ID для externally callable операций с разными правами/логикой. Для динамической регистрации укажи правило, все доступные ветви конфигурации и доказательства охвата. Не выдумывай пути; в отсутствие приложения запиши нулевой инвентарь и подтверждение поиска.

| ID | Метод / операция | Полный путь | Что делает | Доступ | Регистрация | Обработчик |
| --- | --- | --- | --- | --- | --- | --- |

ID стабилен между запусками, пригоден для имени файла и уникален: например `api-v1-get-orders-id`. Коллизии разрешай суффиксом, сохраняя mapping при возобновлении. Укажи текущую git-ревизию/dirty status (если есть), дату, источники документации, область поиска, исключенные неисполняемые fixtures и runtime-условия. `Inventory Review.md` содержит независимое сравнение списка с кодом, исправленные пропуски и `accepted` либо ограничения.

## Версия endpoint-а

Одного commit SHA, timestamp или хеша файла handler-а **недостаточно**. Учитывай текущие незакоммиченные/неотслеживаемые изменения. Построй явный список всех влияющих файлов: регистрация/префиксы, handler, auth/permissions/session middleware, схемы, services, data layer, модели/миграции/constraints, подписывание/crypto, сетевые клиенты, gateway/лимиты, безопасная декларативная конфигурация и dependency lockfiles. Укажи, почему dependency closure полна. Изменение списка зависимостей тоже меняет версию.

Внешние политики, настройки провайдера/БД/gateway, feature flags и зависимости, не отраженные в коде/lockfile, учитывай как отдельные контекстные условия. Не читай настоящие секреты ради сравнения. Если такие условия важны и их неизменность не доказана, нельзя переиспользовать результат. Сначала актуализируй closure по текущему графу вызовов, потом вычисляй hash; не просто повторяй старый список файлов.

Для детерминированного снимка используй стандартный Python 3.10+:

```text
python <skill>/scripts/fingerprint.py --root <project> --files routes/orders.py middleware/auth.py services/orders.py package-lock.json
python <skill>/scripts/fingerprint.py --root <project> --files-from "Security Audit/dependencies/<id>.json"
```

`--files-from` — JSON-массив путей от корня. Скрипт читает только явно перечисленные файлы и выводит JSON `{schema, algorithm, digest, files:[{path, sha256}]}`. Сохрани stdout в `Fingerprints/<id>.json` в UTF-8 средствами среды. Он учитывает bytes на диске и набор путей, отказывается от отсутствующих файлов, symlink, выхода из корня и распространенных файлов секретов. Он **не обнаруживает зависимости**, не доказывает полноту и не проверяет внешнее окружение. Не добавляй секреты с нестандартным именем. Несколько последовательных изменений дерева невозможно атомарно снимковать этим helper-ом; сравни снимок до аудита, после ревью и при финализации. При изменениях/сомнениях перезапусти обе фазы.

Переиспользование возможно только когда совпадают: identity/доступ endpoint-а, полная closure и hash, релевантные внешние условия, покрытие категорий и принятый прежний review. Исторический профиль без этих полей считается неподтвержденной базой. Новый аудитор подтверждает актуальность, а новый ревьюер самостоятельно принимает reuse. Новый checkpoint отмечает `reused`, сохраняя ссылку на прежний принятый результат; не представляй reuse как новый полный аудит.

## Профиль Profiles/<id>.md

- Endpoint ID, метод/путь/операция, описание, модель доступа, дата, run ID, ревизия и dirty status.
- Область анализа, список dependency closure с основаниями, snapshot path/digest, релевантные внешние условия и доказательства их актуальности.
- Режим `audited` / `reused`; для reused ссылка на предыдущие профиль и принятое ревью, точное основание неизменности.
- Таблица **всех 12 категорий** из checks.md: статус, проверенный код, выполненная проверка/основание неприменимости, результат или конкретный blocker.
- Ссылки на все подтвержденные задачи и связь с прежними findings; `0 подтвержденных проблем`, если их нет.
- Выполненные локальные команды, exit codes/наблюдаемые результаты. Невыполненные проверки перечислены отдельно.
- Статус `ready_for_review` до приемки; coordinator отмечает `accepted` / `reused` только по принятому ревью и текущей версии.

## Отдельная задача Tasks/<id>-<issue>.md

```markdown
# <issue-id>: <конкретная проблема>
Endpoint IDs: ...
Severity: critical / high / medium / low (обоснование)
Status: confirmed / resolved / rejected / superseded (текущие доказательства)
Version: <snapshot digest + revision/dirty>

## Доказательства
Файл и точные строки; вход → checks/middleware → sink/эффект.
Вид подтверждения: локальное воспроизведение или доказательство по коду.

## Сценарий атаки
Права и условия атакующего, синтетические шаги/payload, реальный эффект.

## Проверки
Что выполнено и результат; отдельно предложенные regression checks.

## Ожидаемое поведение
Какой инвариант/проверка должен предотвратить атаку.

## Предлагаемое исправление
Конкретный owner layer, мера защиты и регрессионный тест; код не изменен.

## Независимое ревью
Ссылка на review, решение и подтвержденная версия.
```

## Reviews/<id>-<round>.md

ID отдельного ревьюера, дата, версия и область анализа; `accepted` / `changes_requested`. Для **каждой** задачи — решение, свои доказательства, severity, актуальные ссылки и замечания. Отдельно заключение по полноте профиля, «нет findings» или reuse. После устранения замечаний нужен новый reviewer и новый файл раунда; предыдущее решение не переписывай задним числом.

## State.json и Summary.md

State — checkpoint координатора, не источник истины о коде. Минимум: `schema`, `run_id`, `started_at`, `active_seconds`, `last_report_active_seconds`, `goal_owned`, `heartbeat_id`, `endpoints` с `status`, `fingerprint`, `profile`, `review`, `agent_id`, `reason`. Статусы: `pending`, `auditing`, `reviewing`, `changes_requested`, `accepted`, `reused`, `stale`, `blocked`. Различай время этого запуска и исторические результаты. После рестарта pending работы восстанови из кода и файлов.

Summary фиксирует охват `accepted + reused / total`, уникальные подтвержденные проблемы по severity, оставшиеся/blocked категории, документы и выполненную validation. При полном покрытии сообщает завершение **аудита**, а не устранение уязвимостей. Если есть blockers — отчет частичный. Для удаленных endpoint-ов сохраняй исторический результат с пометкой removed и не включай в текущий total; новые endpoint-ы обязательно добавь в очередь.
