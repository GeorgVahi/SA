# Инвентарь, версии и артефакты

Этот reference задаёт контракт данных для `audit`, `fix` и `full`. Порядок работы определяют инструкции выбранного режима; общий checkpoint ведёт координатор. Чтение и запись исходных документов любых форматов описаны в [artifact-formats.md](artifact-formats.md).

## Структура внутри проверяемого проекта

```text
Security Audit/
  Endpoints.md
  Inventory Review.md
  State.json
  Summary.md
  Profiles/<endpoint-id>.md
  Fingerprints/<endpoint-id>.json
  Tasks/<endpoint-id>-<issue-id>.md
  Reviews/<endpoint-id>-<round>.md
  Endpoint Reviews/<исходный путь и формат>
  Remediation/<run-id>/
    Plans/<work-id>-<round>-<version>.md
    Plan Reviews/<work-id>-<round>.md
    Implementations/<work-id>-<round>.md
    Code Reviews/<work-id>-<round>.md
    Snapshots/<work-id>-<phase>-<stage>-<round>.json
  Remediation Summary.md
```

Сохраняй существующие результаты и ручные изменения. Если старый формат не содержит нужных доказательств, дополни его или переаудируй; не удаляй всю папку. Историю значимых ревью/переаудита сохраняй отдельным раундом/запуском. Старые задачи не являются доказательством, что проблема осталась или исправлена: перепроверь и зафиксируй их актуальный статус. Не удаляй вручную написанные задачи молча.

Новые автоматически составленные Endpoint Reviews могут быть `<endpoint-id>.md`; существующие исходные файлы сохраняют пути, вложенность и формат. Прежние Profiles/Tasks/Reviews не перемещай ради нового режима. Перед обновлением текущего принятого профиля сохрани его прежнюю редакцию и связанные доказательства в истории внутри проекта. Снимки координатора имеют отдельную фазу/владельца, не пересекающуюся с путями агентов. Before/after manifests можно хранить внутри snapshot-документа; JSON fingerprint-helper-а сохраняй вложенным объектом или по отдельной ссылке, не меняя его схему.

## Идентичность и связи

| Идентификатор | Контракт |
| --- | --- |
| `endpoint_id` | Стабильная запись метода/операции, нормализованного зарегистрированного пути и сервиса/версии; сохраняется между запусками. |
| `run_id` | Уникальный запуск; сохраняется при продолжении, компакции и рестарте. Новый запуск получает новый namespace со ссылкой на прежний. |
| `work_id` | Одна линия одного исходного файла в данном запуске; стабильно связан с исходным путём. Один файл с несколькими замечаниями имеет один work ID. |
| `issue_id` | Каноническая идентичность уникального дефекта между запусками; не меняется из-за переименования файла, нового endpoint-а или раунда. |
| `attempt_id` | Уникальное назначение фазы; вместе с run/work/phase/round и agent ID отличает текущий результат от запоздалого. |

Сгенерированные компоненты путей безопасны для файловой системы проекта: без разделителей, `..`, зарезервированных имён и коллизий после нормализации регистра. Сохраняй исходное написание пути и ключ сравнения; коллизию разрешай новым ID и явным mapping, без молчаливого объединения файлов. Не выводи endpoint из имени документа.

Реестр содержит доказанные связи `исходный файл + локатор → endpoint IDs → issue IDs → каноническая задача → принятое решение`. Один endpoint может иметь несколько исходных файлов; один файл — несколько endpoint-ов/замечаний; общий дефект — несколько endpoint-ов/файлов. Для каждой связи укажи основания: регистрация, контракт доступа, профиль, task и review с версиями. Неясное соответствие — blocker, а не угаданный маршрут.

Общий дефект получает одну каноническую задачу и одного владельца изменения общего кода. Дубликат содержит `superseded` и `canonical_issue_id`; ссылки на все исходные записи и независимые результаты по всем затронутым endpoint-ам сохраняются. В уникальном счётчике учитывай canonical issue один раз, в таблице файлов — каждую исходную связь. Каноническую задачу нельзя закрыть по одному endpoint-у, если остальные затронутые endpoint-ы ещё не приняты.

Canonical link должен вести к существующей уникальной задаче без циклов/самоссылки; chain дубликатов разрешай до неё, сохраняя исходные связи. Отсутствующий canonical issue или конфликт mapping блокирует финальную приёмку.

## Endpoints.md

Метод + нормализованный зарегистрированный путь + сервис/версия определяют endpoint. Разные методы — разные записи. Для RPC/GraphQL одна транспортная запись с отдельными дочерними ID для externally callable операций с разными правами/логикой. Для динамической регистрации укажи правило, все доступные ветви конфигурации и доказательства охвата. Не выдумывай пути; в отсутствие приложения запиши нулевой инвентарь и подтверждение поиска.

| ID | Метод / операция | Полный путь | Что делает | Доступ | Регистрация | Обработчик |
| --- | --- | --- | --- | --- | --- | --- |

ID стабилен между запусками, пригоден для имени файла и уникален: например `api-v1-get-orders-id`. Коллизии разрешай суффиксом, сохраняя mapping при возобновлении. Укажи текущую git-ревизию/dirty status (если есть), дату, источники документации, область поиска, исключенные неисполняемые fixtures и runtime-условия. `Inventory Review.md` содержит независимое сравнение списка с кодом, исправленные пропуски и `accepted` либо ограничения.

Для удалённого endpoint-а сохраняй identity, прежние результаты, версию и доказательство удаления. Lifecycle `removed` исключает его только из текущего audit total после проверки инвентаря. Удаление одной регистрации не доказывает устранение issue: проверь альтернативные методы, маршруты и достижимые операции.

## Версия endpoint-а

Одного commit SHA, timestamp или хеша файла handler-а **недостаточно**. Учитывай текущие незакоммиченные/неотслеживаемые изменения. Построй явный список всех влияющих файлов: регистрация/префиксы, handler, auth/permissions/session middleware, схемы, services, data layer, модели/миграции/constraints, подписывание/crypto, сетевые клиенты, gateway/лимиты, безопасная декларативная конфигурация и dependency lockfiles. Укажи, почему dependency closure полна. Изменение списка зависимостей тоже меняет версию.

Внешние политики, настройки провайдера/БД/gateway, feature flags и зависимости, не отраженные в коде/lockfile, учитывай как отдельные контекстные условия. Не читай настоящие секреты ради сравнения. Если такие условия важны и их неизменность не доказана, нельзя переиспользовать результат. Сначала актуализируй closure по текущему графу вызовов, потом вычисляй hash; не просто повторяй старый список файлов.

Для детерминированного снимка используй стандартный Python 3.9+; `<python>` — команда из адаптера среды (`python3` или `python`):

```text
<python> <skill>/scripts/fingerprint.py --root <project> --files routes/orders.py middleware/auth.py services/orders.py package-lock.json
<python> <skill>/scripts/fingerprint.py --root <project> --files-from "Security Audit/dependencies/<id>.json"
```

`--files-from` — JSON-массив путей от корня. Скрипт читает только явно перечисленные файлы и выводит JSON `{schema, algorithm, digest, files:[{path, sha256}]}`. Сохрани stdout в `Fingerprints/<id>.json` в UTF-8 средствами среды. Он учитывает bytes на диске и набор путей, отказывается от отсутствующих файлов, symlink, выхода из корня и распространенных файлов секретов. Он **не обнаруживает зависимости**, не доказывает полноту и не проверяет внешнее окружение. Не добавляй секреты с нестандартным именем. Несколько последовательных изменений дерева невозможно атомарно снимковать этим helper-ом; сравни снимок до аудита, после ревью и при финализации. При изменениях/сомнениях перезапусти обе фазы.

Переиспользование возможно только когда совпадают: identity/доступ endpoint-а, полная closure и hash, релевантные внешние условия, покрытие категорий и принятый прежний review. Исторический профиль без этих полей считается неподтвержденной базой. Новый аудитор подтверждает актуальность, а новый ревьюер самостоятельно принимает reuse. Новый checkpoint отмечает `reused`, сохраняя ссылку на прежний принятый результат; не представляй reuse как новый полный аудит.

### Снимки исправления и manifests

Сохрани версии до плана, при принятии его конечной редакции, после внедрения, после ревью и при конечной сверке координатором. Snapshot связывает run/work/phase/stage/round/attempt, время, ревизию/dirty status, обоснованную closure, helper-результат существующей части, manifest, внешние условия и версии входных документов/плана. `stage` различает `before` и `after`; владелец пишет только свои пути. Схема helper-а `schema:1` не является версией State.

Before/after manifests перечисляют объединение влияющих путей обеих версий. Для каждого пути: `path`, `presence` (`present`, `absent` или `unknown` при невозможности установить), SHA-256 присутствующего безопасного файла либо `null` с причиной, способ и время проверки; для отсутствующего — проверяемое свидетельство отсутствия внутри корня. Сравнение доказанных версий отмечает `added`, `removed`, `modified`, `unchanged` и связывает структурное изменение с принятым планом, регистрацией, тестами и task-owned diff. Ошибка доступа не доказывает отсутствие; `unknown`/недоступный необходимый hash остаётся blocker. Связанные/выходящие за корень пути не обходи.

Helper принимает только непустой набор **существующих** безопасных файлов соответствующей версии. Не передавай отсутствующий путь и не создавай заглушки ради хеша. При пустой существующей части запиши `fingerprint: null`, причину и manifest/evidence; это не успешный hash и не достаточное доказательство актуальности. Ошибка helper-а остаётся failed/blocker. Manifest отсутствия требует безопасной проверки файловой системы и, для удалённого endpoint-а, инвентаря/альтернативной достижимости; он не получается из ошибки чтения.

Перед снимком актуализируй closure по текущему графу, включая новые импорты, регистрацию и основания access contract. Baseline включает прежние dirty/untracked изменения; task-owned diff сравнивай с ним, не только с HEAD. Плановое изменение само по себе не конфликт; независимое изменение влияющей зависимости делает решение `stale`. Неотделимый чужой diff — blocker без stash/reset/отката. В `fix` затронутые прежние audit-профили получают `stale`; приёмка исправлений не является полным повторным аудитом.

## Версии входных документов и планов

Версионируй реестр исходных файлов, входной Endpoint Reviews, задачи, принятые профили/reviews, явно записанный access contract и план. Для безопасного документа храни путь, SHA-256 сырых bytes, фактический формат/кодировку и локаторы релевантных записей; для контейнера — внутренние пути. Сохраняй предыдущую редакцию и version/digest принятого решения. Недоступный документ не получает выдуманный digest.

Изменение смысла замечания, контракта, состава документов или принятого содержания инвалидирует зависящие решения даже при неизменном коде. Удалённый исходный документ остаётся в реестре с историей/причиной, а не становится обработанным от исчезновения. Новые/изменённые документы выбранной области возвращаются в подготовку. Перед финалом повтори перечисление и сравнение реестра/версий.

Ожидаемая запись результата собственной фазы не должна делать план бесконечно `stale`. Различай исходное содержание замечаний и выделенный служебный блок/аннотацию результатов. Сохрани raw digest до/после, точный ожидаемый delta, run/round/attempt и ссылку на породивший его вердикт. Подтверди доступным обработчиком, что изменились только выделенные статусы, оценки, ссылки/история и необходимое форматное представление, а смысл замечаний и несвязанные данные сохранились. Такая доказанная запись — выход фазы, а не посторонняя правка её входа; обе версии остаются в истории. Digest выделенного содержания допустим дополнительно, но не заменяет raw digest и проверку delta. Произвольная правка того же блока, неподтверждённый форматный diff и изменение вне ожидаемых границ не игнорируются: затронутая линия возвращается на сверку/перепроверку. Недоказанная сохранность блокирует принятие записи.

Планы неизменяемы по пути `Plans/<work-id>-<round>-<version>.md`. План содержит version, источники/версии, endpoint/issue mapping, перепроверку каждой проблемы, первичный сигнал, owner layer, разрешённый набор записи, closure, порядок изменений, критерии/проверки, совместимость/миграции/rollout, риски и blockers. Принятое решение привязано к **конечной конкретной редакции** и baseline. Дополнение ревьюером создаёт новую version/digest с сохранением прежней; последующая правка принятого содержания требует новой версии и нового независимого review. Digest вычисляй по окончательному файлу и записывай в связанном review/State, без самоссылочного hash внутри хешируемых bytes.

## Профиль Profiles/<id>.md

- Endpoint ID, метод/путь/операция, описание, модель доступа, дата, run ID, ревизия и dirty status.
- Область анализа, список dependency closure с основаниями, snapshot path/digest, релевантные внешние условия и доказательства их актуальности.
- Режим `audited` / `reused`; для reused ссылка на предыдущие профиль и принятое ревью, точное основание неизменности.
- Таблица **всех 12 категорий** из checks.md: статус, проверенный код, выполненная проверка/основание неприменимости, результат или конкретный blocker.
- Ссылки на все подтвержденные задачи и связь с прежними findings; `0 подтвержденных проблем`, если их нет.
- Выполненные локальные команды, exit codes/наблюдаемые результаты. Невыполненные проверки перечислены отдельно.
- Статус `ready_for_review` до приемки; coordinator отмечает `accepted` / `reused` только по принятому ревью и текущей версии.

Статусы категорий — `checked`, `not_applicable`, `blocked` по [checks.md](checks.md). Историческую актуальность профиля после изменения влияющего кода помечай `stale`, сохраняя прежнее решение.

## Отдельная задача Tasks/<id>-<issue>.md

```markdown
# <issue-id>: <конкретная проблема>
Endpoint IDs: ...
Source records: <пути + локаторы + work IDs>
Canonical issue ID: ...
Severity: critical / high / medium / low (обоснование)
Status: <канонический статус из таблицы ниже + текущее основание>
Version: <snapshot digest + revision/dirty + input versions>

## Доказательства
Файл и точные строки; вход → checks/middleware → sink/эффект.
Вид подтверждения: локальное воспроизведение или доказательство по коду.

## Сценарий атаки
Права и условия атакующего, синтетические шаги/payload, реальный эффект.

## Проверки
Что выполнено и результат; отдельно предложенные regression checks.

## Ожидаемое поведение
Какой инвариант/проверка должен предотвратить атаку.

## Предлагаемое исправление / принятое исправление
Owner layer, мера защиты и необходимые проверки; ссылки на plan/implementation.
В audit это предложение: код приложения не изменён.

## Независимое решение и история
Review, версия, run/round/attempt, статус, основание и локальная область приёмки.
История прежних решений; canonical link для superseded; rollout отдельно.
```

Исходные доказательства не копируй между папками: ссылайся на них. В audit задачи создают только для доказанных дефектов. В fix канонический статус синхронизирует только координатор по принятому вердикту; code-review роль пишет свой review и исходный документ, не общую задачу.

## Reviews/<id>-<round>.md

ID отдельного ревьюера, дата, версия и область анализа; `accepted` / `changes_requested`. Для **каждой** задачи — решение, свои доказательства, severity, актуальные ссылки и замечания. Отдельно заключение по полноте профиля, «нет findings» или reuse. После устранения замечаний нужен новый reviewer и новый файл раунда; предыдущее решение не переписывай задним числом.

## Endpoint Reviews и артефакты исправления

После принятого аудита координатор создаёт Endpoint Reviews по ссылкам на профиль, канонические задачи и принятые reviews; это не дополнительное независимое ревью. При наличии только старых Profiles/Tasks/Reviews дополни ими новую входную запись без удаления/перемещения оригиналов. При существующей папке рекурсивно учитывай **все** файлы, сохраняя ручной текст, формат и историю. Служебные элементы получают доказанное назначение; непрочитанный/неоднозначный файл не исчезает из реестра.

Исходник содержит endpoint ID, метод/маршрут, профиль/audit review с версиями и каждую запись с canonical issue ID/task. После приёмки туда записываются текущие статус/оценка, локальная область, проверенная версия и ссылка на независимое решение. История содержит run/round/version/attempt; прежние выводы отделены от текущих. Для бинарного/структурированного документа используй локаторы и подходящее место записи по [artifact-formats.md](artifact-formats.md).

| Артефакт | Обязательное содержание |
| --- | --- |
| `Plan Reviews` | Новый reviewer/attempt, `accepted` / `changes_requested` / `blocked`, конечная version/digest плана, baseline/input versions, собственная перепроверка каждой записи, достаточность критериев/наборов файлов, изменения плана и ограничения. |
| `Implementations` | Принятые plan/review, attempt, выделенные файлы, task-owned diff, before/after snapshots/manifests, команды/exit codes/результаты, первичный сигнал до/после, совместимость, миграции и ограничения. Проверка общего фикса записана явно без повторного патча. |
| `Code Reviews` | Новый reviewer/attempt, план/digest, implementation и текущая версия, независимая проверка каждого issue/применимости общего фикса, сохранение допустимого поведения, новые дефекты патча, вердикт, статус/основание, оценка/объяснение, собственные проверки/ограничения, input/output versions исходника. |

Отчёт исполнителя не подменяет независимый сигнал. Нет патча этого запуска при `already_resolved`/`rejected` — нет фиктивного implementation и оценки нового фикса; независимое подтверждение хранится в Plan Reviews. Принятый общий фикс текущего запуска требует собственного подтверждения для каждого затронутого исходного файла/endpoint-а.

Для раннего конечного решения по Plan Reviews координатор записывает актуальные `already_resolved`/`rejected`, `—` и ссылку на это решение в исходный документ, проверяет запись и синхронизирует task/State. Для `no_recorded_findings` достаточно полного чтения, результата в реестре и строки сводки: обязательной аннотации исходника нет, `write_state: not_required` имеет явное основание, raw version сохраняется. Это не фиктивное ревью кода и не разрешение координатору самому принять issue.

## Канонические статусы и оценки

Исполнение файла, audit-профиль, вердикт ревью и статус issue — разные поля. `phase: code_review` не означает `resolved`.

| Статус issue | Значение | Уникальный остаток |
| --- | --- | --- |
| `confirmed` | Актуальный независимо подтверждённый дефект. | Да |
| `partial` | Патч внесён, но критерии устранения выполнены не полностью. | Да |
| `blocked` | Необходимое доказательство, доступ/проверка недоступны; причина и недостающее условие записаны. | Да, отдельно как блокировка |
| `stale` | Решение зависит от изменившейся влияющей версии. | Да до перепроверки |
| `resolved` | Исправление этого запуска независимо принято на актуальной версии. | Нет |
| `already_resolved` | Устранено до этого запуска; независимая текущая проверка это доказала. | Нет |
| `rejected` | Нарушение опровергнуто проверкой контракта и кода. | Нет |
| `superseded` | Дубликат с обязательной ссылкой на canonical issue. | По канонической задаче |

`resolved` требует одновременно актуальной версии, `accepted` независимого review, разрыва достижимости исходного сценария/существенных обходов, сохранения допустимого поведения и успешных необходимых проверок. Failed, timeout, непроверенная обязательная область/недоступное необходимое runtime-условие не дают `resolved`. Для общего issue нужны принятые результаты всех затронутых endpoint-ов. Статус относится к проверенному **локальному** дереву/условиям, не доказывает устранение в production. Rollout фиксируй отдельно; необходимая для самого исправления непроверенная миграция остаётся blocker.

Оценка качества — целое число 1–10 с основанием; severity оценивает ущерб отдельно. **Числового порога приёмки нет**: число не открывает/закрывает issue. Оценка 7 совместима с `resolved`, если обязательные критерии доказаны; противоречие оценки и вердикта требует объяснения/проверки доказательств.

| Оценка | Основание |
| --- | --- |
| 1–3 | Сценарий сохраняется или патч создаёт существенную новую проблему. |
| 4–6 | Частичное устранение; обходы, нарушение совместимости или failed checks. |
| 7 | Обязательные критерии доказаны; остаются несущественные замечания к сопровождаемости/дополнительные улучшения. |
| 8 | Устранение в owner layer, необходимые проверки прошли, существенных замечаний нет. |
| 9 | Дополнительно проверены существенные границы и допустимое поведение. |
| 10 | Сильные независимые доказательства релевантных критериев, без выявленных недостатков в проверенной области; не гарантия отсутствия любых уязвимостей. |

Храни оценки каждого замечания. Оценка файла — минимум числовых оценок; без выполненного исправления это `—` (в JSON `null`), в том числе для `already_resolved`, `rejected`, `no_recorded_findings` и непрочитанного файла. Минимум не скрывает unresolved записи с `—`. Полностью обработанный файл требует доказанных конечных результатов всех записей, актуальных связей и проверенной записи в исходный формат. `no_recorded_findings` — результат **полного чтения документа** без записанных замечаний, а не новый вывод об отсутствии уязвимостей в коде; это результат файла, не статус canonical issue.

## State.json: schema 2 и совместимость

State — checkpoint координатора, не источник истины о коде/транзакционная БД. `schema: 2` — версия нового контракта; сохраняй валидный JSON, даты UTC ISO 8601, длительности в секундах. Недоступные значения — `null` с причиной, не успех. Пути относительны корню проекта либо явно объявленному `Security Audit/`; база пути однозначна. Счётчики вычисляются из актуальных связей и сами не дают приёмку.

В новом checkpoint `endpoints`, `source_registry`, `work_items`, `issues` — JSON-объекты по endpoint ID, work ID, work ID и issue ID соответственно. Legacy `endpoints` в форме массива или объекта сохраняй при совместимой миграции вместе со всеми записями/неизвестными полями; установи проверяемый ID mapping для доступа без разрушительного преобразования старого представления. Недоказанная идентичность остаётся blocker. Запись source хранит исходный путь и при необходимости массив members/локаторов контейнера; histories и списки связей — массивы. `ownership`, `waves`, `timing`, `synchronizations`, `compatibility` — объекты с описанными ниже данными; записи синхронизации идентифицируются run/work/issue/attempt. Для неиспользуемой в текущем режиме области сохраняй пустой объект/массив с основанием, не выдумывай завершённую фазу.

| Поле | Минимальное содержание |
| --- | --- |
| `schema`, `run_id`, `started_at`, `updated_at` | Версия 2, идентичность/время текущего запуска, связь с предыдущей историей. |
| `mode`, `scope`, `status` | `audit` / `fix` / `full`, точная область/полномочия, общий `running` / `partial` / `complete`. Не статус goal. |
| `active_seconds`, `last_report_active_seconds` | Накопленное активное время и отметка часовой сводки; не обнуляются при рестарте. |
| `goal_owned`, `heartbeat_id` | Принадлежность goal и ID фактически созданного таймера/heartbeat среды (см. адаптер) либо `null`; сохранить имеющиеся goal ID/основания. |
| `platform`, `skill_root`, `platform_context` | Среда координатора, абсолютный корень скилла для заданий ролей и повторного чтения после компакции, данные адаптера среды (конфигурация проекта, ограничения, worktree) в формате адаптера. |
| `endpoints` | Прежние audit-записи: status, fingerprint, profile, review, agent_id, reason; lifecycle, версии и история. |
| `source_registry` | Все исходные пути, work ID, lifecycle (`present` / `removed`), назначение, формат/encoding/BOM/newlines, handler/доказанные возможности, raw versions/локаторы, состояния чтения/записи, endpoint/issue mapping и blockers; внутренние пути контейнеров. |
| `work_items` | По work ID: исходник, endpoint/issue IDs, исполнение/фаза, round/attempt/agent ID, input/plan versions, phase artifacts/snapshots, разрешённая запись/ownership, blockers, вердикт/история. |
| `issues` | Canonical task, severity/status/основание, canonical link дубликата, исходные записи/затронутые endpoint-ы, локальные принятые результаты, оценки/версии/независимые решения, rollout отдельно. |
| `ownership` | Координатор и владельцы путей/наборов записи/влияющих зависимостей, attempt и подтверждение передачи/освобождения. Неизвестный владелец не означает свободный файл. |
| `waves` | Full-волна, результаты аудита/исправлений, история критериев/версий и `no_progress_waves`. |
| `timing` | Длительности фаз/линий, реальные слоты/параллельность, активные интервалы, ETA range/основание либо недостаток данных, неизвестное время внешних blockers. |
| `synchronizations` | Code Reviews → исходник → task → State: expected/current versions, `pending` / `complete` / `blocked`, выполненные шаги/конфликт. |
| `compatibility` | Исходная schema/сохранённая legacy-версия, преобразования, сохранённые неизвестные поля и ограничения миграции. |

Audit endpoint status сохраняет: `pending`, `auditing`, `reviewing`, `changes_requested`, `accepted`, `reused`, `stale`, `blocked`; removed — отдельный lifecycle. Work status: `pending`, `running`, `changes_requested`, `complete`, `stale`, `blocked`; `phase`: `preparation`, `planning`, `plan_review`, `implementing`, `code_review`, `done`. `complete` не определяется номером фазы/оценкой. `read_state` исходника: `pending` / `read` / `blocked`; `write_state`: `pending` / `verified` / `not_required` / `blocked` с основанием. `no_recorded_findings` сохраняй отдельно как результат источника. Служебное назначение и отсутствие записанных замечаний подтверждай чтением, не расширением.

В каждой линии раздельно сохраняй `no_progress_planning_rounds`, `no_progress_implementation_rounds`, завершённые раунды и доказательства продвижения/сброса; в full — `no_progress_waves`. Три последовательных завершённых раунда/волны без продвижения требуют целевой независимой переоценки по workflow; общего потолка продуктивных раундов нет. Смена agent/run/version, косметика и рестарт не сбрасывают счётчик. Ожидание/пауза не завершённый раунд. Новую принятую причину/способ с проверяемым продвижением сохраняй до сброса.

При `schema:1` распознанного audit-checkpoint сохрани исходный корректный документ в истории внутри проекта, audit-поля/endpoints, время, IDs и неизвестные совместимые поля; добавь schema 2 и запись миграции. Отсутствующий режим можно восстановить как `audit` только по доказанному историческому контракту, без разрешения на fix. При отсутствии schema сначала установи совместимость, не присваивай 1/2 вслепую. Неизвестную несовместимую schema, повреждённый State и конфликт полей не обнуляй: сохрани файл/последнюю корректную копию, запиши blocker миграции и восстанавливай доказуемое из артефактов без разрушительной перезаписи. Старый `complete` не означает завершённые fix/full. Неизвестное поле не удаляй только потому, что его нет в таблице.

### Сохранение и согласование checkpoint

При смене фазы, принятии/отклонении и перед финалом записывай checkpoint через временный файл **внутри проекта**: сериализация, повторный parse/проверки связей/версий, затем безопасная замена при подтверждённом единственном владельце. Сохрани последнюю корректную версию до замены. При недоступной безопасной замене/ошибке I/O не заявляй сохранение и не удаляй прежний файл. Это не новый runtime и не обещание атомарности нескольких документов.

Приёмка требует полной согласованной связки артефактов и текущих версий. После сбоя координатор сверяет Code Reviews, исходник, canonical task, State и код; идемпотентно завершает недостающую синхронизацию по тому же актуальному решению, не дублируя историю. Частичная запись остаётся `pending`/`blocked`. Конфликтующие актуальные вердикты требуют нового независимого решения, не выбора по timestamp.

После рестарта/компакции сверяй реально работающих агентов, attempt IDs, код и документы. Исчезнувший агент возвращает работу в очередь; saved `running` не доказательство работы. До передачи записи подтвердить завершение/остановку прежнего владельца; timeout не доказывает освобождение. Запоздалый результат иной попытки не становится текущим. Прерванное внедрение сначала сверяется с baseline/diff/проверками без слепого повторного патча. Доказанно завершённый неизменный результат не повторяй.

## Сводки и полный охват

`Summary.md` сохраняет охват аудита `accepted + reused / current total`, уникальные confirmed проблемы по severity, оставшиеся/blocked категории, документы, выполненную validation и ограничения. Полный аудит не означает устранение уязвимостей. Removed endpoint-ы сохраняются в истории, новые обязательно попадают в очередь.

Во всех режимах checkpoint позволяет подготовить сводку каждый час активной работы: режим/фаза, обработанные/все файлы, завершённые audit endpoint-ы, уникальные resolved/already_resolved/rejected/активные/blocked проблемы, остаток файлов/задач, фазы и существенные результаты. Время включает ожидание работающих агентов, исключает пользовательскую паузу/неработающий сеанс. ETA — диапазон по минимум трём сопоставимым завершённым линиям либо достаточным замерам фаз с реальными слотами/критическим путём. Без данных укажи недостаток измерений; время внешнего blocker — неизвестно. Запись времени/heartbeat ID не доказывает фоновую доставку.

Для fix/full `Remediation Summary.md` и сообщение пользователю содержат **ровно четыре столбца**:

| Файл | Эндпоинт | Замечание | Оценка |
| --- | --- | --- | --- |
| `<исходный путь>` | `<метод и маршрут / операция>` | `<issue ID>: <описание>; <статус>; <ссылка на независимое решение>` | `<1–10 или —>` |

Одна строка — одно замечание; для нескольких повторяй файл/endpoint. Общий дефект отражён во всех исходниках, считается одной уникальной задачей. Прочитанный файл без записанных замечаний — строка `no_recorded_findings`, оценка `—`. Непрочитанный документ, неоднозначная связь, служебный/удалённый файл и препятствие записи — отдельная строка с конкретным результатом/ограничением и `—`; неизвестный endpoint обозначай как неустановленный. Вложенные записи показывай с member locator. Реестр не исчезает из таблицы из-за расширения, удаления файла или отсутствия оценки.

Перед таблицей — счётчики полного охвата/уникального остатка; после — выполненные проверки, primary/independent signals, актуальность аудита, ограничения, миграции/rollout и git-результат. Зафиксируй run ID, конечную ревизию/dirty state, локальную область приёмки и состояние развёртывания отдельно. Неприменимое обозначай явно, не подменяй passed.

Полное fix завершение требует всех исходных файлов и проверенной необходимой записи в них; конечных независимых результатов `resolved` / `already_resolved` / `rejected` для всех unique issues и ссылок дубликатов; отсутствия pending/active/partial/blocked/stale и ожидающего обязательного review; согласованных конечных версий/связей и успешных необходимых проверок. Пустая очередь и прочитанные документы без findings — отдельные доказанные результаты, не обещание нового аудита. Full дополнительно требует полного актуального аудита всех текущих endpoint-ов. Любой остаток делает отчёт частичным; высокая оценка, старый accepted или checkpoint `complete` этого не отменяют.
