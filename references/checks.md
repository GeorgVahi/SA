# Проверки и стандарт доказательств

Прочитай обработчик вместе с middleware, сервисами, запросами к данным, схемами, конфигурацией доступа и тестами. Для каждой категории ниже выбери `checked`, `not_applicable` или `blocked`, укажи основание и проверенный участок. `checked` означает выполненную релевантную проверку, а не гарантию безопасности. Недоступное runtime-условие не превращай в not_applicable.

Выбирай самый короткий достаточный сигнал для конкретного риска: проверяемая цепочка по коду или локальный сценарий нарушения инварианта. Не повторяй одинаковые успешные одиночные вызовы ради числа assertions и не создавай тесты, пересказывающие реализацию. Несколько запросов оправданы для конкретного replay/race-сценария или разных границ входа; укажи это основание. После успешного сигнала расширяй/повторяй проверку только при изменении кода, провале, непокрытой ветви или оставшемся конкретном риске. В профиле сохраняй краткие команды и результаты, а не многократно продублированные логи.

| Категория | Что проверить по фактической цепочке вызовов |
| --- | --- |
| IDOR и авторизация | Права на объект/tenant при чтении и записи, роли, server-side owner binding, обход через альтернативный маршрут/метод, массовое присваивание защищенных полей. |
| Инъекции | SQL/NoSQL, shell, шаблоны, LDAP, заголовки, HTML/JS (XSS) и XML/XXE; проследи контролируемый вход до опасного sink и фактическое экранирование/параметризацию. |
| SSRF | URL от пользователя до сетевого клиента, допустимые схемы/хосты, redirect, приватные адреса, DNS; учитывай реально достижимый egress и существующие ограничения. |
| Файлы | Path traversal, download authorization, upload size/type, опасные имена, распаковку архивов, overwrite, выполнение и доступ к хранилищу. |
| Вебхуки | Подпись исходного тела, доверенный источник, timestamp, replay/deduplication, порядок проверок до побочных эффектов. |
| CSRF | Cookie-based auth, изменяющие состояние действия, токены/Origin/SameSite, CORS и простые запросы; CORS сам по себе не доказательство CSRF-защиты. |
| Секреты | Утечки через ответы, ошибки, логи и исходный код, права доступа и границы доверия. Реальные значения не копируй в отчет или вывод. |
| Платежи | Server-side сумма/валюта/товар, подлинность события провайдера, состояния заказа, ownership, refund, идемпотентность и уникальные ограничения. |
| Повторы | Replay действий/токенов, идемпотентность, атомарный deduplication, одноразовые операции и повторная доставка событий. |
| Гонки | Check-then-act, транзакции, locks/unique constraints, одновременные списания/выдача ресурсов; отсутствие lock без достижимого нарушения инварианта не находка. |
| Входы | Типы/размеры/границы, unexpected fields, нормализация, опасная десериализация, login/recovery/session/token flow и привязка учетной записи. |
| Лимиты | Реально дорогостоящие операции, pagination/body/timeout, brute force, quota и ограничения на уровне gateway/middleware/storage. |

## Когда создавать задачу

Нужны доказанный достижимый вход, возможность атакующего управлять им при указанных условиях, отсутствие/обход применимых защит, конкретный эффект и точные места кода. Подтверждение — безопасное локальное воспроизведение с синтетическими данными **или** полная проверяемая цепочка в исходниках. Запуск не обязателен, если код полностью доказывает проблему; явно различай эти виды доказательства. Если релевантная защита неизвестна или зависит от непроверенной внешней конфигурации, записывай ограничение проверки, а не подтвержденную уязвимость.

Для IDOR/авторизации докажи также нарушенное правило доступа по документации, тестам или однозначному контракту доменной модели. Поле `owner`/`tenant` само по себе не доказывает запрет чтения другим пользователем: общие или публичные объекты могут допускать такой доступ. При неясной политике укажи недостающий контракт как ограничение; успешное чтение чужого объекта без доказанного запрета не становится подтвержденной задачей.

Не записывай «может быть SQL injection», «нет rate limiter» или «вероятна гонка» без доказанной цепочки и ущерба. Severity определяй по фактическому impact и prerequisites; critical — для доказанного критического эффекта, не по названию категории. CVSS можно указывать только с обоснованным вектором. Отсутствие findings не отменяет обязательный профиль и ревью.

В задаче предложи конкретное исправление в owner layer и значимый regression test: как воспроизвести до исправления и какое поведение должно быть после. Не редактируй production-код и не выдавай предложенный тест за выполненный.

Используй file:line по текущему дереву и fingerprint; ссылки ревьюера должны совпадать с проверенным кодом. Для web/GitHub-ссылок укажи ревизию, если она известна; для незакоммиченного кода используй пути от корня и диапазон строк в тексте. Все примеры payload и ответы обезличены. Не включай настоящие cookies, токены, адреса клиентов или ключи даже в цитаты.
