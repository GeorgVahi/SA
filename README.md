# SA — аудит и исправление безопасности для Codex

Один скилл **`$SA`**: проверка эндпоинтов, исправление подтверждённых замечаний или полный цикл. Каждый этап проверки выполняют новые сабагенты с чистым контекстом; данные и история находятся в `Security Audit/` текущего проекта.

## Установка на ПК

Нужны Codex с локальными скиллами и Python 3.10+. Python-пакеты, API-ключи и внешние сервисы для установки не требуются.

```powershell
git clone https://github.com/GeorgVahi/SA.git
cd SA
python scripts/install.py
```

По умолчанию устанавливается в `~/.agents/skills/SA`, глобально для текущего пользователя и всех его проектов. Если ваша версия/конфигурация Codex использует другой каталог скиллов:

```powershell
python scripts/install.py --skills-dir "$env:USERPROFILE/.codex/skills"
```

Устанавливайте в один обнаруживаемый каталог, чтобы не получить дубликаты. Установщик копирует только файлы скилла и сохраняет manifest. Существующий скилл не перезаписывает. Обновление установленной этим скриптом версии:

```powershell
git pull --ff-only
python scripts/install.py --update
```

Используйте тот же `--skills-dir`, если меняли каталог. При ручных изменениях, неизвестных файлах или конфликте «файл ↔ каталог» обновление останавливается до записи: сначала сохраните и согласуйте свои правки или миграцию структуры. Неуспешное I/O-обновление не считается установленной версией; сверяйте файлы перед повтором. Скрипт не меняет `config.toml`, модели, разрешения или Git-конфигурацию.

Откройте чат в нужном проекте и введите `$SA`. Если скилл не появился, перезапустите Codex. Локальные скиллы и их обнаружение описаны в [официальной документации](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills). Имя `SA` сохранено в верхнем регистре для точного вызова `$SA`; типовой валидатор skill-creator требует lowercase, поэтому проверка имени этим валидатором не проходит. Обнаружение имени проверяется реальным `skills/list` Codex, остальные поля — отдельной проверкой структуры.

## Использование

| Запрос | Результат |
| --- | --- |
| `$SA audit` | Полный инвентарь с независимой проверкой, аудит и независимое ревью каждого эндпоинта; приложение не исправляется |
| `$SA fix` | Актуализация записанных замечаний и четыре роли для каждого исходного файла: план → ревью плана → внедрение → ревью кода |
| `$SA full` | Аудит → исправления принятых находок → повторный аудит затронутых эндпоинтов на конечном коде |
| `$SA Продолжи существующий запуск` | Восстановление выбранного режима, очереди, версий, владельцев и накопленного времени |

Можно указать режим естественной просьбой. При одном `$SA` скилл задаёт один вопрос с тремя вариантами; до ответа приложение не меняется. Явно выбранный режим не требует повторных подтверждений обычного локального плана и патча. Это инструкции агента, а не отдельные CLI-команды.

При повторном аудите инвентарь снова сверяется с текущим кодом. Reuse возможен только при принятом прежнем ревью и доказанном совпадении всей влияющей dependency closure, bytes на диске, контракта доступа и внешних условий. Его подтверждает новый ревьюер. Commit SHA и неизменившийся handler сами по себе недостаточны.

## Исправления и приёмка

`fix` читает все файлы Endpoint Reviews рекурсивно. Старые Profiles/Tasks/Reviews сохраняются и получают связанные документы для исправления. Формат и кодировка не ограничивают область: для текстов, PDF/офисных документов, структурированных файлов, сканов, контейнеров и других типов выбирается подходящий доступный обработчик. Результат записывается в тот же исходный файл с сохранением несвязанных данных и проверкой повторного чтения. Реальное препятствие чтения/сохранения явно отражается в очереди; отдельный отчёт не подменяет незавершённую запись источника.

Первый агент перепроверяет реальность замечаний и пишет план. Второй независимо проверяет и при необходимости дополняет его новой версией. Третий внедряет принятый план и необходимые regression checks. Четвёртый не пишет код приложения: самостоятельно проверяет результат и записывает статус, доказательства и оценку 1–10. Already-resolved и rejected требуют доказанного независимого подтверждения; фиктивный патч для них не создаётся.

Статус устранения определяется доказательствами, актуальным независимым вердиктом и успешными обязательными проверками. Числового порога нет; оценка описывает качество отдельно. Локальный resolved не означает выполненный production-rollout.

Разные файлы обрабатываются параллельно по фактическим слотам; запись общей зависимости сериализуется. Один общий дефект исправляется один раз, но применимость к каждому исходному файлу подтверждается свежими ролями. Канонический issue закрывается после подтверждения всех затронутых endpoint-контекстов.

Общего лимита продуктивных попыток нет. Три последовательных раунда без доказанного продвижения вызывают независимую переоценку; при новом обоснованном пути работа продолжается, иначе сохраняется blocker. Смена агента и косметические изменения не считаются прогрессом. Checkpoint предотвращает потерю очереди, истории и повторный запуск конкурирующих писателей.

## Что проверяется

Все 12 категорий: IDOR/авторизация, инъекции, SSRF, файлы, вебхуки, CSRF, секреты, платежи, повторы, гонки, входы и лимиты. Каждая категория имеет доказательство выполненной проверки, основание неприменимости или конкретный blocker. Задачи создаются только по доказанной достижимой цепочке нарушения контракта; например, само поле owner не доказывает запрет общего чтения.

## Результаты

```text
Security Audit/
  Endpoints.md, Inventory Review.md
  State.json, Summary.md
  Profiles/, Fingerprints/, Tasks/, Reviews/
  Endpoint Reviews/                 исходные документы по эндпоинтам
  Remediation/<run-id>/
    Plans/, Plan Reviews/, Implementations/, Code Reviews/, Snapshots/
  Remediation Summary.md
```

Прежние поля checkpoint сохраняются при переходе к schema 2; формат fingerprint-helper остаётся отдельным. История запусков/версий не перезаписывается. Финальная сводка fix/full охватывает каждый исходный файл, одна строка на замечание:

| Файл | Эндпоинт | Замечание | Оценка |
| --- | --- | --- | --- |

Статус и ссылка на ревью входят в описание замечания. Файлы без записанных findings имеют отдельную строку и оценку —. Дубликаты показаны во всех источниках, но уникальные задачи считаются один раз.

Каждый час активной работы сообщается прогресс, остаток файлов/уникальных задач, blockers и ETA диапазоном по реальным замерам и фактической параллельности. Обычные краткие updates сохраняются. Продолжение восстанавливает время. Для отдельно запрошенной доставки при неактивном чате нужен доступный heartbeat; скилл и установщик не создают постоянный процесс автоматически.

Недоступная независимая роль, stale версия, провал обязательной проверки или blocker дают честный частичный результат и очередь. Аудит с найденной уязвимостью может быть завершён; исправления — только после доказанного результата всех задач. Full дополнительно подтверждает актуальность полного аудита на конечном коде.

## Границы доступа

Безопасные локальные проверки и синтетические данные. Production, реальные платежи/вебхуки, чужие данные, разрушительные миграции, новые production-зависимости/инфраструктура и выход за полномочия требуют соответствующего разрешения. Секреты и персональные данные не выводятся. Публикация отчётов об уязвимостях требует явной авторизации именно на находки; обычного git autopublish недостаточно. Внешние worktree не создаются. Скилл не гарантирует обнаружение всех возможных уязвимостей.
