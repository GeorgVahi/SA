## Вопросы, поставленные ревьюером

### Q1. Делать ли оценку 8 обязательным порогом?

Основание сомнения: пользователь просит независимую оценку 1–10, но не задаёт порог успешности. План добавляет `>=8`. Код и документы не дают калибровки числовых оценок разных ревьюеров.

Варианты: оставить обязательные objective gates плюс порог 8; либо закрывать issue по доказанному контракту/проверкам/актуальному accepted review, оставляя число отдельной оценкой качества. Рекомендация: второй вариант, если число нужно для отчёта; первый допустим как явно выбранная более строгая политика. Последствие первого: исправление может оставаться открытым из-за расхождения субъективных оценок, даже при выполненных проверяемых требованиях. Порог в плане не изменён скрытым решением ревьюера.

### Q2. Что делать после трёх неудачных попыток или волн?

Основание сомнения: исходный запрос ориентирован на обработку всех файлов и не задаёт численного лимита. Три попытки и три full-волны являются предложением плана; данных о длительности и сходимости нового процесса нет.

Варианты: завершать этот запуск честным частичным отчётом/checkpoint; либо продолжать при наличии нового обоснованного способа исправления, ограничивая только повторение одинаковой безуспешной попытки. Рекомендация: сохранить защиту от повторяющихся неуспешных кругов, но обсуждать точный лимит как настраиваемую политику, а не доказанно достаточное число. Последствие жёсткого лимита: нужен следующий запуск даже когда технический путь ещё существует. Последствие отсутствия лимита: расход ресурсов может расти без полезного прогресса. Текущие лимиты не заменяют правила goal-инструмента и не позволяют объявить полный успех.

### Q3. Часовая сводка — для всех режимов и какого времени?

Основание сомнения: исходная логика задаёт час в процессе исправлений; текущий аудит имеет два часа. План выбирает единый час активной работы для всех режимов. Доставка при неактивном чате требует отдельно доступного и разрешённого heartbeat; сам скилл не гарантирует её.

Варианты: сохранить единый активный час; либо оставить два часа для самостоятельного audit и час для fix/full. Рекомендация: единый активный час, как сейчас в плане, с измеряемым checkpoint и честным ограничением фоновой доставки. Если пользователю нужен именно календарный час при неактивном чате, это отдельное требование к доступному расписанию, которое надо фактически проверить. Изменение audit-интервала — выбранная политика плана, не прямое следствие исходного запроса на исправления.

### Q4. Какие исторические форматы Endpoint Reviews должны поддерживаться?

Основание сомнения: текущий tracked-формат SA не определяет Endpoint Reviews, а примеров реальных исторических файлов в рассмотренных источниках нет. Нельзя подтвердить совместимость с произвольными документами только по тексту плана.

Варианты: определить обязательный контракт для Markdown/UTF-8 text, отражая остальные форматы как явный blocker; либо включить дополнительные форматы, которые доступны инструментам среды, с сохранением исходного файла и безопасным добавлением статуса. Рекомендация: сначала проверить синтетические legacy-сценарии, затем обезличенные представительные образцы фактически используемых форматов; не вводить новые зависимости или автоматическую конверсию без доказанной необходимости. Последствие узкого контракта: часть исходных файлов может остаться blocked. Последствие обещания всех форматов: появляются неподтверждённые требования к чтению и записи, особенно для бинарных документов. План правильно запрещает молча исключать такие файлы, но не доказывает возможность их обработки.

В плане предусмотрены три последовательных раунда/волны без доказанного продвижения, затем целевая независимая переоценка. Согласование закрывает выбор политики, но не подтверждает будущую реализацию. К сценариям плана добавлены проверки независимости оценки/статуса, продуктивных попыток сверх трёх и обработки разных форматов/кодировок. Новая независимая проверка реализации предстоит на соответствующем этапе.

## Проверки независимого ревью и ограничения

Первичный сигнал: завершено прямое сопоставление исходной логики, плана и текущих owner-документов/helper-кода; выявленные выше пробелы устранены в плане. Вторичный сигнал: документарные проверки завершены:

- `git diff --check` — exit 0, ошибок пробелов в tracked diff нет; `git diff -- docs/SA-MODERNIZATION-PLAN.md` просмотрен целиком.
- `python -B -` с проверкой в памяти средствами стандартной библиотеки — exit 0: оба документа UTF-8, конечный newline и отсутствие trailing whitespace, уникальные заголовки, парные code fences; все 19 локальных Markdown-ссылок существуют внутри проекта. Нумерация будущих сценариев 1–19 согласована; это проверка текста, не исполнение сценариев.
- `git status --short --branch` — exit 0: ветка `main`, изменён только план, новый файл только данный отчёт. Runtime-файлы не изменены.
- Отдельный discovery-поиск `rg --files ... -g AGENTS.md` по целевым каталогам завершился exit 1 из-за отсутствия совпадений; он не объявляется прошедшей runtime-валидацией. Проверка наличия AGENTS в корне/предках также не нашла файлов.

Будущие сценарии, helpers unit tests, runtime-загрузка нового скилла, новая/обновлённая установка и часы фоновой доставки в этом ревью не проверялись: задача меняет только документационный план. Исторические passed результаты из VALIDATION.md не переобозначаются как результаты данного ревью. Production, реальные секреты, внешние сервисы и реальные данные не использовались.

Документация: обновлён только план и создан данный отчёт. Миграция/rollout текущему изменению не нужны; миграция State, новых артефактов и обновление установленного скилла относятся к будущей реализации. Git-результат: изменения оставлены локально, без commit/push по ограничениям задания.
