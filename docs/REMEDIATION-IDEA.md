# Предложение: исправление замечаний после SA

Дата: 11 октября 2026.

Статус: зафиксирована логика пользователя для обсуждения. Расширение скилла, аудит и исправления не запускаются. Выбор между новым скиллом и режимами существующего SA пока не принят.

## Исходная формулировка пользователя

> Пройди по очереди все файлы внутри Security Audit / Endpoint Reviews , если там записаны реальные замечания безопасности, для этого файла(если там такие замечания есть) создай сабагента с чистым контекстом - пусть напишет план на устранение замечаний безопасности. По готовому плану новым сабагентом с чистым контекстным окном сделай ревью плана - пусть дополнит этот план если это необходимо. И третьим сабагентом с чистым контекстом внедри этот план.
> после внедрения, запусти четвертого на код ревью, пусть даст оценку внесенным изменениям(без написания кода) и запишет в том же файле статус этих замечаний безопасности(пофикшено ли и насколько хорошо) и свою оценку этого фикса от 1 до 10.
> эту логику примени к каждому файлу, можешь запускать параллельно по несколько файлов из Endpoint Reviews , главное чтобы сабагенты не перепутались.
> в процессе раз в час присылай текущий прогресс и количество отсавшихся задач с примерной оценкой времени которое еще потребуется.
> а как закончишь - сделай полный отчет в виде списка с оценками по каждому из проверенных файлов в формате таблицы:
> файл - эндпоит - замечание - оценка

## Зафиксированные требования

1. Это следующий этап после базового аудита SA.
2. Обойти все файлы в `Security Audit/Endpoint Reviews/`. Запускать исправления для файла, если в нём есть реальные замечания безопасности.
3. Для каждого такого файла последовательно использовать четыре разных новых сабагента с чистым контекстом:
   - Первый пишет план устранения замечаний.
   - Второй делает независимое ревью готового плана и дополняет его при необходимости.
   - Третий внедряет проверенный план.
   - Четвёртый проводит ревью внесённых изменений, не пишет код приложения и записывает в исходный файл статус замечаний, качество исправления и оценку от 1 до 10.
4. Повторить процесс для каждого файла. Допустима параллельная обработка нескольких файлов, при сохранении последовательности фаз внутри каждого файла и однозначной принадлежности агентов к своему файлу.
5. Раз в час сообщать текущий прогресс, количество оставшихся задач и примерное время до завершения.
6. По завершении подготовить полный табличный отчёт по каждому проверенному файлу:

| Файл | Эндпоинт | Замечание | Оценка |
| --- | --- | --- | --- |

## Предложенный пользователем вариант запуска

После вызова скилла предложить выбор:

- Аудит текущих/новых эндпоинтов.
- Исправление имеющихся замечаний безопасности.
- Оба этапа по очереди: аудит → исправление.

Это вариант для обсуждения, а не уже принятое изменение интерфейса скилла.

## Расхождения с текущим SA для будущего согласования

- Текущий SA явно исключает исправление кода приложения. Новый этап потребует отдельного определения разрешённых действий.
- Текущий формат использует `Profiles/`, `Tasks/` и `Reviews/`; `Endpoint Reviews/` в нём не определён. Путь из исходного запроса сохранён без подмены. Сопоставление с существующими артефактами ещё предстоит выбрать.
- Базовый аудит сейчас предусматривает подробный отчёт каждые два часа активной работы. Для предложенного этапа пользователь указал один час.

Действующие `SKILL.md`, references, скрипты и установленная версия скилла этим документом не меняются.
